# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

PeakCam is a live mountain webcam and snow report aggregator, in production at https://www.peakcam.io (Vercel, auto-deploy on push to main). Stack: Next.js 16 (App Router), React 19, Supabase (Postgres + Auth), Tailwind CSS 4, MapLibre GL (react-map-gl), Resend, PostHog. ~148 resorts and ~350 cam rows seeded from `data/*.csv`.

## Commands

```bash
npm run dev              # Dev server (localhost:3000)
npm run build            # Production build
npm run lint             # ESLint (flat config, next/core-web-vitals + TS)
npx tsc --noEmit         # Type check
npm test                 # node:test via tsx — lib/*.test.ts + scripts/*.test.ts
npm run drop-in:sync-three   # Re-vendor public/drop-in/three.module.js after bumping `three`

# Data & ops scripts (all load .env.local themselves, write via service-role key)
npm run import-resorts:standalone  # Seed resorts/cams from data/*.csv (the maintained importer). A newly-imported resort has no live page until the next deploy — /resorts/[slug] uses dynamicParams=false, so its static params list is fixed at build time.
npm run snotel-sync      # SNOTEL sync — the production data feed for NRCS-station resorts (launchd runs it every 6h)
npm run model-sync       # Open-Meteo sync for resorts without a SNOTEL station (South America etc.; launchd every 6h)
npm run stations-sync    # Station layer: up to 3 stations per resort by elevation band (SNOTEL, GHCN, NWS obs, BC ASWS, ECCC) → stations/resort_stations/station_observations; launchd hourly. `--dry-run --resort alta` needs no service key
npm run approach-cams-sync  # DOT road cams (Caltrans, DriveBC open; UDOT/WSDOT/COtrip behind env keys) → cams rows with kind=approach; run by hand
npm run pipeline-sync    # Multi-source pipeline (currently dormant in prod — see Gotchas)
npm run seed-normals     # SNOTEL normals: 1991–2020 SWE/depth percentiles plus the 30- and 10-winter cumulative new-snow normal and monthly climatology (migration 030; run once, then every October; `--dry-run`, `--station`)
npm run snotel-backfill  # Ten water years of daily SNOTEL rows into snowpack_daily with the sync's QC and daily new snow (run once; idempotent; `--dry-run`, `--resort slug`, `--years N`)
npm run cam-health       # Probe all cam URLs, stamp cams.last_checked_at
npx tsx scripts/import-profiles.ts --dry-run   # Validate data/resort-profiles.csv; drop the flag to PATCH resorts' profile columns (needs migration 025)
```

There are no `liftie-sync` / `snodas-sync` npm scripts — that logic lives in `lib/pipeline/fetchers/` and runs only via `pipeline-sync`. `npm run import-resorts` (the ts-node variant) is stale and truncates SNOTEL triplet IDs — use `:standalone`.

## Architecture

### Read path (the site)

Every data-bearing page is a thin Server Component with ISR (`export const revalidate = 3600`) that fetches via `lib/supabase.ts` (anon-key client) and passes the full dataset as props to one large `"use client"` component that owns all interactivity. There is no client-side fetching of resort/snow data. `getAllResorts()` runs 3 queries (active resorts, `latest_snow_reports` view, active cams) and stitches them into `ResortWithData[]` in JS.

- `/` → `BrowsePage` (Fuse.js search, filter chips, sort incl. curated `POPULAR_SLUGS`, optional map sidebar)
- `/resorts/[slug]` → SSG via `generateStaticParams` + live NWS forecast (`lib/weather.ts`) + crowd reports; dynamic OG image. **Page family** (parity plan P2, registry in `lib/resort-pages.ts`): `/resorts/[slug]/snow-report` (today's numbers with dates, 7-day `snowpack_daily` history, forecast, user-report count, station link) and `/resorts/[slug]/webcams` (every cam click-to-play via `components/cam/CamPlayer.tsx`, per-cam health and still-archive strip). Each subpage is a Server Component with the same ISR/`dynamicParams=false` contract, its own `BreadcrumbList` + `WebPage.dateModified`, a markdown alternate at `…/index.md`, a `Link` header (`next.config.ts`) and a sitemap entry; the tab row (`components/resort/ResortTabs.tsx`) links them. Forecast and History tabs are block 2.
- Resort page JSON-LD: `SkiResort`+`TouristAttraction` (with `additionalProperty` rows, `sameAs` incl. Wikidata, `hasMap` from the profile columns), `BreadcrumbList`, `WebPage` (`speakable` → `#resort-freshness`), `Event` "{Resort} {season} season opening" from `resort_openings` while the date is ahead, `FAQPage` from `lib/resort-faq.ts` (identity questions first; the same array renders visibly in `ResortAboutSection`), `VideoObject` per live stream.
- Resort profile columns (`runs_total`, `lifts_total`, `skiable_acres`, `vertical_ft`, `annual_snowfall_in`, `longest_run_mi`, `passes`, `trail_map_url`, `wikidata_id`, `elevation_base_ft`, `elevation_summit_ft`, `description`, `description_source`, `aliases`; migration 025 from block P0) are optional on `Resort` and every consumer (`lib/resort-profile.ts`) drops a sentence rather than printing null. Source data: `data/resort-profiles.csv` (operator stat pages, official pass lists, Wikidata search); `npx tsx scripts/import-profiles.ts --dry-run` validates, without the flag it PATCHes `resorts` by slug with the service-role key. A stored `description` renders under the hero with its source label and in the markdown alternate as `Description (source): …`.
- `/map` → MapLibre full-page map with clustered GeoJSON (`lib/map-utils.ts`) + RainViewer radar
- `/compare`, `/snow-report`, `/favorites`, `/dashboard` (client-only, react-grid-layout), `/auth`, `/alerts/manage`

Cam embeds are click-to-play by `embed_type`: `youtube` (autoplay+mute embed), `iframe`, `image` (30s cache-buster auto-refresh), `link` (link-out). Cam tiles carry `CamReportButton` → `/api/cam-reports/submit`.

### Three Supabase clients — pick the right one

- `lib/supabase.ts` — module-level anon client + all public read queries. Throws at import if env vars missing (affects builds).
- `lib/supabase-browser.ts` — `@supabase/ssr` browser client for Client Components needing auth (favorites, dashboard, auth UI).
- `lib/supabase-server.ts` — cookie-bound server client for Route Handlers / Server Components needing the user session (RLS as the user).

`proxy.ts` (Next 16 middleware successor) refreshes the Supabase session on every non-static request.

### Write path (API routes)

Route handlers under `app/api/` (30 `route.ts` files as of 2026-10-20; P4 added `v1/resorts/[slug]/forecast` and `forecast-accuracy`), each with its own auth model: alerts subscribe/manage/unsubscribe (capability `manage_token`, service-role writes, deny-all RLS; `manage` also adds/tests/removes webhook destinations), `alerts/trigger` (Bearer `CRON_SECRET`; Vercel cron daily 13:00 UTC per `vercel.json`; writes a `powder_alert_runs` row, fans out Standard-Webhooks deliveries, `maxDuration` 60), `conditions/vote` (anonymous, localStorage session UUID), `user-conditions/submit` (auth session + RLS + profanity flag), `cam-reports/submit` (anonymous, validated by `lib/cam-reports/validate.ts`, salted IP hash, Resend admin email), `csp-report` (CSP violation sink, 1-in-20 sampled to PostHog), `v1/*` (public read-only JSON API, no auth; `v1/batch` and `v1/ask` also take POST but write nothing), `mcp` (read-only MCP server, no auth).

### Data ingestion — two pipelines, one live

1. **`scripts/snotel-sync.ts` — the production feed** (launchd `com.peakcam.snotel-sync`, every 6h). NRCS AWDB API → QC via `lib/snow-quality.ts` (range/spike checks, carry-forward) → `snowpack_daily` → full conditions engine (normals, 7-day SWE history, user reports, NWS grid) → appends `snow_reports` (source='snotel') + patches `resorts.cond_rating`. `scripts/model-sync.ts` mirrors it for the ~59 resorts with no SNOTEL station, using the Open-Meteo model (source='open_meteo'). Together these two scripts are the only things feeding the live site's snow report. `scripts/stations-sync.ts` (hourly) fills the station layer beside it (migration 026) and `scripts/approach-cams-sync.ts` adds DOT road cams; neither touches `snow_reports` or `cond_rating`. The forecast tables (027) have their own pair since P4 (2026-10-20): **`scripts/forecast-sync.ts`** (launchd `com.peakcam.forecast-sync`, every 6 h, `RunAtLoad`) asks Open-Meteo for every model at once (`models=` in `lib/forecast/open-meteo-models.ts`: ECMWF IFS, GFS, GEM, ICON, JMA, Météo-France, UKMO, plus NBM and HRRR for US points; 14 days, the parser keeps each model's real horizon) at the summit and base elevations of every active resort → one `forecast_runs` row per model per point with `forecast_daily` rows, idempotent per issue hour, retention in `lib/forecast/retention.ts` (newest run per model per UTC day after 7 days, delete after 120 days except a model's last row); and **`scripts/forecast-score.ts`** (`com.peakcam.forecast-score`, daily 07:30 local, after snotel-sync) which grades every model's day-1/3/7 forecasts against SNOTEL depth deltas (clipped at zero; `lib/forecast/score.ts`, GHCN fallback via the P3 station tables) over 90 days and rewrites `forecast_scores` with a `blend` row. The blend itself (`lib/forecast/blend.ts`: per-day median, 25th/75th band, `modelCount`, totals, peak) is computed on read from the stored runs, so the page, the API and the MCP tools can never show different numbers. `--dry-run --resort <slug>` on either script writes nothing (the sync needs only the anon key then).
2. **`lib/pipeline/` — multi-source blender** (SNOTEL + NWS + Liftie + SNODAS + Weather Unlocked + user reports → `data_source_readings` + `resort_conditions_summary`). Code-complete but dormant: its launchd job has never succeeded (plist missing PATH), the blender has stubbed inputs (pct_of_normal=null, NWS grid fields never populated, elevation hardcoded), and no UI code reads its output tables. Both pipelines write `snow_reports` and overwrite `resorts.cond_rating` — last writer wins.

### Conditions engine

`lib/conditions-engine.ts` — pure functions: rating thresholds (`RATING_THRESHOLDS`), 7-day trend, outlook ladder, tag/narrative synthesis, and a 70/30 SNOTEL/user-report blend (needs ≥2 unflagged reports, clamped ±1 tier). `lib/snow-quality.ts` holds QC + water-year math. Keep these pure — scripts and (nominally) the pipeline both import them.

### Database

34 tables + 4 views in `public` as of 2026-10-18 (migrations through `028`; 2026-10-18 added `powder_alert_runs`, `alert_destinations` in 023, `cams.archive_allowed` + `cam_stills` + view `cam_still_timeline` in 024, and the parity data model in 025–028: resort profile columns + `elevation_base_ft`/`elevation_summit_ft` on `resorts` (backfilled from `resort_metadata`, which is now the legacy copy), `cams.kind/credit/source_terms_url`, `cam_timelapses`, `stations`, `resort_stations`, `station_observations`, `forecast_runs`, `forecast_daily`, `forecast_scores` (filled by the P4 jobs since 2026-10-20: ~10 k run rows and ~110 k daily rows a day at 148 resorts before thinning, see `lib/forecast/retention.ts`), `resort_scores` — the others empty until their P3–P8 jobs land; see `docs/runbook.md` "Parity data model"; note that 022's `cam_stills` table was never applied in prod, 024 created it). Migration 030 (P5, 2026-10-19; apply before the backfill) adds `snowpack_daily.new_snow_in`, the cumulative-normal columns on `snotel_normals` (prod shape is `median_swe/p10_swe/p90_swe/median_depth/p10_depth/p90_depth`, not the 005 file's names), the `snotel_monthly_normals` table and the `season_stats(powder_in, season_start, week_start)` SQL function the leaderboards read; the reads fail soft until it is applied. Migrations are applied **by hand** (SQL Editor / MCP `apply_migration`) — there is no Supabase CLI config, numbering is documentation only, and 004/005 each have two files. RLS postures: public-read (catalog/snow tables), anon-insert (`condition_votes`, `agent_memory`), auth.uid()-scoped (`user_conditions`, `user_favorites`, `dashboard_layouts`), deny-all/service-role-only (alerts tables, `cam_reports`).

Known live-DB drift from the repo migrations (verify against prod before trusting a migration file):
- `user_conditions.snow_quality`: the 004 file still checks `icy/slush`, but prod's CHECK is already `powder/packed/crud/ice/spring` (changed by hand; matches code and UI). Migration 019 records the prod definition idempotently.
- `user_conditions` timestamp column: 004 says `submitted_at`; prod has `created_at`. Code used `submitted_at` for months (PostgREST 400 → "No recent reports", zero user reports in the sync blend, rate limit failing open). Reconciled in code — every consumer now reads `created_at` — and documented by migration 019 (renames only if `submitted_at` still exists; no-op on prod).
- `latest_snow_reports` exposes `resorts.id AS resort_id` (migration 029) so a per-resort filter pushes down to one index probe; keep that when recreating it. It was created as `SELECT *` in 001; columns added to `snow_reports` by 005/007 required manual view recreation in prod — no migration records it.
- `cams` carries a hand-applied unique constraint `cams_unique_per_resort` on `(resort_id, name, COALESCE(embed_url,''), COALESCE(youtube_id,''))` that exists in no migration file, beside migration 012's `cams_resort_embed_url_idx` on `(resort_id, embed_url, name)`. The importer's upsert targets the 012 index, where a NULL `embed_url` never conflicts, so a YouTube-only row that already exists goes to INSERT and fails with 23505 on the constraint (observed 2026-10-18: Deer Valley "Ontario Snowstake", batch 4 of 7). `scripts/import-resorts-standalone.mjs` therefore reads the table first and skips rows already present under that four-column identity (`camIdentity()` / `partitionCamRecords()`). Every other prod index also exists only in the live DB.
- `latest_snow_reports` is hit ~12k times/day by the anon role, which has a 3s `statement_timeout`; the view must stay index-friendly (see migration 018).

`snow_reports.conditions` is an overloaded string: `"tag1,tag2||narrative"`. Consumers must split on `||` (done in ConditionsStrip, ComparePage, map-utils). Don't add new consumers without unpacking it.

### Drop In (`/resorts/[slug]/drop-in`)

A self-contained arcade ski descent, live for three pilot resorts (`ski-portillo`, `breckenridge`, `heavenly`). Entry points: the map popup card, the mobile bottom sheet, and the resort detail page — all gated on `isDropInResort()`.

`public/drop-in/engine.html` is the entire game in one file (markup, CSS, and an inline module) and imports a **vendored** `three.module.js` beside it. It is a bundler-free static asset, so it carries its own copy of every resort profile: **`RESORT_PROFILES` in the engine and `PROFILES` in `lib/drop-in.ts` must stay in sync by hand**, and `scripts/drop-in-engine.test.ts` fails the build if they drift. The host mounts it in an iframe sandboxed *without* `allow-same-origin` (`components/drop-in/DropInFrame.tsx`) — the engine therefore has an opaque origin, cannot touch app cookies, and announces itself over `postMessage` authenticated by `event.source`, not by origin. `proxy.ts` excludes `/drop-in/` so the static assets skip the Supabase session round-trip.

### Adjacent subsystems (same repo, not part of the web app)

- `agents/` — 9-bot Slack "company" (`agents/loop.mjs`, polling + Anthropic API, shared memory in `agent_memory`). Runs via launchd but is effectively dormant.
- `dashboard/` — standalone Express ops dashboard on port 3333. **Unauthenticated and can spawn `claude --dangerously-skip-permissions`** — never expose beyond localhost/LAN.

## Key Patterns & Gotchas

- Path alias `@/*` maps to the repo root (`tsconfig.json`).
- MapLibre (`components/map/MapView.tsx`) must be loaded with `dynamic(..., { ssr: false })`.
- `snow_reports` is append-only; the latest row per resort comes from the `latest_snow_reports` view.
- Powder threshold (8") is hardcoded in multiple places — grep before changing it. The resort count in UI copy is computed from data; page metadata says "150+".
- Forecast snow amounts come from the stored multi-model blend (`lib/forecast/*`, served through `lib/public-api/forecast.ts`); `lib/weather.ts` keeps the NWS wording, temperatures and wind and only falls back to its keyword heuristic (`snowSource: "nws_keyword"`) when no run is stored for the resort. Anything that serves blend numbers must carry "Weather data by Open-Meteo.com" (CC BY 4.0).
- Two auth UX flows coexist: `/auth` page (email+password) and `AuthModal` (magic link). Both land on `/auth/callback`.
- Docs trust: `GEMINI.md` is an accurate high-level overview; `docs/runbook.md` has stale schedules; `UX-AUDIT-PLAN*.md` are executed historical artifacts.
