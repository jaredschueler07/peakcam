# Startup waterfall removal

Branch `feat/drop-in-v3-load-time`, based on integratione223b94. No GPU/browser launched and no timing target changed.

1. TerrainAssetLoader starts metadata, trails and height fetches together. Metadata refines the byte-weighted progress denominator but no longer blocks the large transfers. Shared versioned URLs live in `config/terrain-assets.ts`; progress stays monotonic and capped below1 until every asset succeeds. A failed pack request aborts its siblings; aborted requests emit no later progress.
2. createGame starts terrain loading and WebGPU initialization concurrently. Once a WebGPU backend is initialized, node-factory loading overlaps any remaining terrain transfer. Explicit/unsupported WebGL never loads node factories. `startWhenWarm` remains awaited after complete resource initialization, so loading does not resolve early or weaken shader readiness.
3. The pilot game page emits only its selected resort's three versioned `as=fetch` preload hints before the resort-data await. No engine or terrain preload was added to other pages/off-roster pages. Hints use anonymous CORS (same-origin credentials); TerrainAssetLoader explicitly uses cors/same-origin fetch semantics and exactly the same URLs so the browser can reuse preloads.

Ownership: the startup helper owns a successfully initialized injected backend until it returns all resources. Terrain/node failure or cancellation aborts peer work and disposes that backend once. GPU initialization itself cannot be cancelled; a late successful backend sees the cancelled controller and disposes itself without loading nodes or constructing a runtime. Aborts reject promptly even while a node import/init promise remains pending, with all late failures observed. Ownership transfers to GameRuntime on construction; startup abort during prewarm disposes the runtime, and any later created/disposed guard remains idempotent. Failed `selectRendererBackend` retains its existing fallback contract: it returns undefined and owns no successfully initialized backend. We deliberately do not call Three `renderer.dispose()` on failed init: installed0.185's dispose calls async setAnimationLoop(null), which retries the rejected init and could create an unhandled rejection. No backend factory behavior changed.

Validation:32 focused loader/startup/backend tests pass, including unresolved metadata concurrency, peer cancellation, early/late abort, node failure, late successful backend cleanup, successful ownership transfer, no-node WebGL fallback and preserved warmup tests. TypeScript no-emit and ESLint changed modules pass; diff check clean. Actual cold10Mbps/100ms production remeasurement and preload-response reuse in browser remain root-owned. No claim that the3s cold-ready budget is met until measured.
